# Native iOS in Swift: migration plan

Status: proposed, 23 September 2026. Nothing here is implemented. The Capacitor app
([MOBILE_PLAN.md](MOBILE_PLAN.md), phases P0–P4) works and stays shippable throughout.

## Objective

Rebuild the app as a native iOS application in Swift, because iOS is now the product rather than a
port of it. Four reasons, all of which the current architecture answers poorly:

- **It feels like a web view**, because it is one. Scrolling, navigation and gesture handling are
  approximations of the platform rather than the platform.
- **Compute is interpreted.** The planner's colour-neutral sweep is ~1.9 s of JavaScript, and the
  190,080-position BFS cross table costs ~490 ms to build. AOT-compiled Swift should be
  dramatically faster — but see the honesty note below, because this has never been measured on a
  phone.
- **The platform is out of reach.** Live Activities, widgets, background BLE and Shortcuts are the
  capabilities that would make this feel like a real cubing app, and Capacitor does not open them.
- **Learning Swift is an explicit goal**, which changes the arithmetic: the port is not pure cost.

The web app is scaffolding at this point and may be frozen. It is *not* deleted — see below, it has
one more job to do.

## The one real risk, and the answer to it

The expensive thing here is not the 9,300 lines of logic. It is the **8,630 lines of tests**, which
encode corpus-derived percentile baselines, CFOP segmentation edge cases (pseudoslotting, keyhole,
OLL/PLL skips), property tests over the move engine, and the differential test proving the GAN
protocol against a reference implementation over 1,213 real frames of the actual cube. Reimplementing
logic is tractable. Rebuilding that confidence from nothing is not, and it is the part that gets
underestimated.

**So the TypeScript does not get thrown away. It becomes the oracle.**

This is the trick P2 already proved: `gan-web-bluetooth` was kept as a devDependency so the vendored
protocol could be diffed against it on every run, and that comparison caught real divergences. The
same pattern applies to the whole port, and more strongly — because these are pure functions with
no radio attached:

> For each pure package, a generator walks the existing tests and fixtures, runs the TS
> implementation over a broad input space, and writes `(input, expected)` vectors as JSON. The
> Swift implementation asserts against those vectors.

That converts *"rebuild the test suite"* into *"generate fixtures and write assertion harnesses"*,
which is an order of magnitude cheaper and produces **more** coverage than hand-written tests, not
less. Where a TS test checks one scramble, a generated corpus can check ten thousand.

Everything below is sequenced so that no Swift code is written before its oracle exists.

## What ports, and how

| Piece | Lines | How it ports |
|---|---:|---|
| `engine` | 1,149 | Direct. Typed arrays → `[UInt8]`. `tables.generated.ts` → JSON. |
| `analysis` | 753 | Direct, pure. |
| `solver` | 1,014 | Direct, and where Swift should win biggest — tight integer loops over fixed tables. |
| `metrics` | 1,458 | Direct. `baselines.generated.ts` (552 lines of corpus percentiles) → JSON, unchanged. |
| `planner` | 2,447 | Direct. `weights.generated.ts` → JSON; the MLP forward pass is ~40 lines of Swift. |
| `session` | ~700 | Recorder and stats port; the stores are replaced by SwiftData or SQLite. |
| GAN protocol | 1,378 | Port. AES-128-CBC comes from CryptoKit; the `BleTransport` seam is replaced by CoreBluetooth directly. |
| Tracker, timeline | ~400 | Direct, pure. The least-squares clock fit is the same arithmetic. |
| UI | 4,797 | Rewrite in SwiftUI. Not a port. |

Two dependencies have no Swift equivalent and are the real unknowns:

- ~~**`cubing/scramble`**~~ — **resolved in S1.** No solver is needed: WCA scrambles cost 9 ms and
  59 bytes each to generate, so a bundled pool regenerated by a build step replaces the port
  entirely. See S1 for the finite-supply caveat.
- ~~**`cubing/twisty`**~~ — **resolved in S1.** ~180 lines of SceneKit renders a cube from a facelet
  string and turns a layer correctly, verified visually.

Untouched by all of this: the Python training pipeline in [ml/](ml), the corpus tooling, and the
findings in the README. The model is 377 parameters of JSON either way.

## An honesty note on performance

Of the four motivations, performance is the one that has **never been measured on the phone**. P5
exists to do exactly that and has not run. If the planner turns out to be acceptable on device, one
of the four reasons evaporates — and if it is slow, the cheapest fix is already scoped: defaulting
to preferred cross colours removes six sevenths of the work for an afternoon.

That does not argue against the migration, given the other three reasons. It argues for **running
P5 first**, so the decision is made against a number rather than an assumption, and so there is a
baseline to show the Swift version beating.

## Phases

Ordered so a working native app exists early, and so the three genuinely unknown things are proven
before anything depends on them. Weekend units, as [PLAN.md](PLAN.md) uses.

### S0 — Measure, and build the oracle · 1 weekend · no Swift · **done**

- Run P5's measurement half: time the colour-neutral sweep and the cross-table build on the iPhone.
  Record the numbers. This is the baseline the Swift port is judged against.
- Write `tools/vectors/`: generators that run the TS packages over broad input spaces and emit JSON
  `(input, expected)` corpora for engine, analysis, solver, metrics and planner.
- Commit the vectors. Add a TS test asserting the generators reproduce them, so the oracle cannot
  drift from the implementation it describes.

**Shipped.** The measurement came out of P5: an iPhone 11 runs the planner at **2.4× a desktop**,
not the order of magnitude that was feared — so the performance argument for this migration is the
weak one, and the case rests on native feel, platform capabilities and learning Swift. That is a
decision to take knowingly, which was the point of measuring first.

The oracle is `vectors/`: **5,400 cases, 2.1 MB**, generated by `npm run vectors` and committed.
Engine (3,000), solver (1,200) and analysis (1,200), each a `(input, expected)` corpus stated
entirely in facelet strings, notation, numbers and booleans — nothing that requires the Swift port
to exist before it can read its own test data. `tools/vectors/test/vectors.test.ts` regenerates from
the recorded seed and fails if the implementation has moved, so the recording cannot quietly stop
describing the code.

**One finding, and it is the reason to verify a test rather than trust it.** The drift test was
checked by perturbing `isStandardOrientation` and watching it fail — and it *passed*. The corpus was
built from `randomMoveScramble`, which emits only face turns, so every position sat in standard
orientation: the centres never moved, and `normalizeOrientation` and `isStandardOrientation` were
exercised only where they are trivially the identity. A Swift port could have got both completely
wrong and the vectors would have agreed with it. A third of positions now carry whole-cube
rotations, and the same perturbation fails as it should.

All five corpora now exist — **6,660 cases, 2.7 MB** — and every one was checked by perturbing the
implementation it describes and confirming the drift test fails:

| Corpus | Cases | Pins |
|---|---:|---|
| `engine` | 3,000 | move application, notation round-trips, orientation |
| `solver` | 1,200 | exact cross distance, optimal length and count |
| `analysis` | 1,200 | CFOP segmentation, including which inputs fail and why |
| `planner` | 1,200 | cross features, comfort, and the committed MLP weights |
| `metrics` | 60 | per-phase timings, pauses, fluidity and corpus ratings |

`metrics` is bounded by its inputs rather than by a seed: synthetic solves mostly fail to segment,
so it is built from the twenty verified reconstructions in `reconstructions.json` under three
timing profiles each — steady, slow start, and one long mid-solve pause, because pause detection
and fluidity are precisely what a single flat profile never exercises.

`planner` records the model score alongside the features that produced it, which ties
`weights.generated.ts` into the oracle: a port that reads the weights or the feature order wrongly
still returns plausible numbers and merely gives worse advice, so it has to be pinned rather than
inferred. That is the same failure the PyTorch parity fixture guards on the other side of the same
boundary.

### S1 — Three spikes · 1–2 weekends · throwaway code · **done, all three pass**

Timeboxed, and each answers a question that changes the plan if the answer is no:

1. **A cube in SceneKit** — 27 cubies, arbitrary state from a facelet string, an animated quarter
   turn, drag to rotate. *Can the renderer be matched?*
2. **A scramble** — bind or port a two-phase solver and verify its output against
   `randomScrambleForEvent` via the engine's own verifier. *Are WCA scrambles reachable?*
3. **A connected cube** — CoreBluetooth scan, manufacturer-data MAC, CryptoKit AES-128-CBC,
   decode one Gen4 move frame. Check it against `gan-gen4-frames.json`, which already holds 1,213
   real frames and their expected decode. *Does the protocol port cleanly?*

**All three answered yes**, and two of them more cheaply than the plan assumed. Code is in
`spikes/CubeSpikes` (a SwiftPM package, `swift test` and `swift run CubeRenderSpike`) and is
throwaway by design.

**1. The renderer — yes, ~180 lines.** A `SCNNode` of 27 cubies painted from a 54-character facelet
string, rendered offscreen to PNG so the result could actually be looked at rather than assumed.
Verified visually: a solved cube shows six uniform faces across two camera angles, and freezing an
R turn at 45° shows exactly the right slice twisted with the rest stationary. The first camera
placement used Euler angles and showed L/F/D instead of U/F/R — a camera positioned at a corner
looking at the origin avoids guessing at sign conventions.

**2. The scrambler — yes, and no solver is needed.** This was scoped as the real risk: WCA
random-state scrambles were assumed to need a two-phase Kociemba solver ported or bound into
Swift. Measured instead: generating them with the existing cubing.js pipeline costs **9 ms each**
and **59 bytes each**, so a pool of 10,000 is **0.56 MB and 1.5 minutes to build**. Ship the pool
as a bundled resource, regenerate it in a build step, and the Swift app needs no solver at all.

  The one property to respect is that a pool is finite. Sampling it randomly makes a repeat likely
  after roughly 120 solves out of 10,000 — recognisable, in an app where you look hard at every
  scramble — so scrambles should be consumed in a shuffled order and marked used, which makes the
  supply exactly its size. Porting a solver stays available later as a way to make it infinite; it
  is no longer on the critical path.

**3. The protocol — yes, mechanical.** A Swift decoder reproduces the TypeScript's decode of the
committed 1,213-frame capture exactly: 1,063 MOVE, 138 FACELETS, 11 BATTERY, one unrecognised,
zero invalid face encodings, monotonic cube timestamps, and the cube clock tracking the host to
within 1%. That is an independent implementation in a different language agreeing with both the
TypeScript and the reference library on real hardware bytes.

  One correction to this plan: **CryptoKit does not do AES-CBC.** It offers GCM, ChaCha20-Poly1305
  and key wrapping only. `CommonCrypto` does, it is a system framework with nothing to add, and the
  scheme is single-block anyway.

What this changes: the two things the plan called "the real unknowns" are no longer unknown, and
one of them stopped being work. The remaining risk in the migration is volume, not feasibility.

### S2 — The pure core · 3–4 weekends · **done**

`engine` → `analysis` → `solver` → `metrics` → `planner`, bottom-up, each asserted against its S0
vectors before the next begins. Dependency-free and mechanical; this is the bulk of the lines and
the least of the risk.

Measure the solver and planner against S0's numbers as soon as they run. That is the moment the
performance claim becomes a fact or stops being one.

**Engine: done and passing.** `swift/CubingCore` is the real package — unlike `spikes/`, it is
meant to survive — and its engine reproduces all **3,000 recorded cases**: move application,
composition, notation round-trips, rotations and wide moves. The oracle worked exactly as intended:
no hand-written expectations were needed, and the two failures it caught were both real.

Notes from doing it:

- **The move tables are generated into Swift**, by `npm run swift-tables`, from
  `tables.generated.ts` rather than re-derived from cubing.js. That way the two implementations
  cannot disagree about what a move *is* — only about what they do with it, which is the thing the
  vectors test.
- **Notation is hand-written**, because cubing.js has no Swift equivalent. It covers the subset the
  app produces and consumes, and preserves two behaviours worth keeping: layer-prefixed moves
  (`2U`, `3Rw`) are rejected rather than silently applied as `U`, and whole rotations (`R4`) are
  dropped as the no-ops they are. Commutator and conjugate syntax is out of scope; nothing the app
  writes uses it, though feeding the reconstruction corpus to Swift directly would need it.
- **The core needs no Foundation import.** Stripping `//` comments by hand rather than reaching for
  `range(of:)` keeps it pure computation, which is worth preserving for a module that may end up
  somewhere constrained.

**Analysis, solver, metrics and the cross planner: done and passing.** 21 Swift tests, every recorded
case in all five corpora. `npm run swift-tables` now also emits the corpus baselines and the MLP
weights as Swift (`tools/vectors/swift-data.ts`), for the same reason as the move tables.

The oracle did its job three times over, and twice the fault was in the oracle or the TypeScript,
not the port:

- **The analysis corpus barely tested segmentation.** 1,192 of its 1,200 cases were
  `does-not-solve`, because a cross plus random noise almost never solves the cube. Half the cases
  now undo their scramble outright; 607 segment. A planted `<`→`<=` in the pseudoslot rule is caught.
- **The metrics generator was recording a field that does not exist** (`fluidityBand` is on the
  score, not the metrics) and the key was silently dropped from the JSON. `tools/` was never in the
  typecheck. It is now, and the corpus records duration, TPS, recognition and pause threshold too.
- **`comfortScore` tie-breaking was floating-point noise.** Two frames turning the same faces the
  same number of times should tie exactly and let the first frame win; summed move by move they
  differed in the last bit, so rounding picked the frame, and Swift's `log` rounded differently
  from V8's. Fixed in the TypeScript (summed per face in a fixed order), all 779 tests still pass,
  and the planner corpus now records each plan's framed text, hold and setup rotation so this
  class of disagreement is visible.

**Performance, measured on the desktop (release build before the remaining S2 ports):**

| | TypeScript | Swift |
|---|---|---|
| All six cross tables, cold | 515–591 ms | **54 ms** (~10×) |
| 200 positions × 6 colours, cross-only plan | 83 ms | 73 ms |
| … of which the search itself | — | 26 ms |

The table build is the real win and it is large. The cross-only planner is at parity, because two
thirds of its time is presentation: every candidate (up to 200 per colour) is re-framed four ways
and given a setup rotation, and the Swift data model makes that expensive — `Move.family` is a
`String`, and `CubeState` is five heap-allocated arrays. Two cheap fixes (hashable moves instead of
interpolated string keys, a cached permutation table) took it from 103 ms to 73 ms, and the
structural refactor described below took it to 56 ms.

**Remaining S2 core port: done.** The 24-case `vectors/s2.json` oracle records pair distances,
xcross lengths and counts for all four slots, preserving next-pair insertions, wide-move respelling,
pair model features and scores, and complete `planColour` outputs with lookahead. All 25 release
Swift tests pass against the recorded TypeScript behaviour; the TypeScript suite passes 782 tests.
`rank.ts` and `scorer.ts` are ported with the pair and cross model weights. `decisions.ts` and
`explain.ts` feed solve review in `planner.worker.ts`; `grip.ts` feeds `SolveDetail.tsx`. Those are
S5 review work, outside the S2 colour sweep.

The structural refactor stores move families as `UInt8` IDs and the five cube piece arrays in
fixed-size value storage. Both cross and xcross formatting wait until ranking has selected the
kept plans. The search also reuses inverse edge positions for the cross bound at each F2L node.

**P5's fixed-position desktop workload, Swift release build, warm tables:**

| | TypeScript P5 | Swift after S2 |
|---|---:|---:|
| Full six-colour sweep, median of three | 2.32 s | **1.41 s** |
| One colour | 425 ms | **253 ms** |
| Next pair + lookahead | 161 ms | **32 ms** |

The Swift sweep is about 1.6× faster on this desktop.

**On the phone — the number checkpoint 3 asks for.** The same workload on the same iPhone 11 that
produced P5's baseline, two cold launches of a Release build:

| | TypeScript in WKWebView (P5) | Swift | Speedup |
|---|---:|---:|---:|
| Cross tables, cold | 2,208 ms | **136–142 ms** | ~16× |
| One colour | 966 ms | **660 ms** | 1.5× |
| Colour-neutral sweep, median | 5.45 s | **3.74–3.91 s** | 1.4× |
| Next pair + lookahead | 372 ms | **86 ms** | 4.3× |

The TypeScript workload has not moved since P5 — it still measures 2.33 s on the desktop — so the
comparison is like for like.

**Two corrections, made in S5.** The "next pair + lookahead" figures above (32 ms desktop, 86 ms
phone) were wrong: the Swift `Lookahead.pairs` split `continueF2L`'s 400,000-node default between
the slots where the TypeScript splits 1,600,000, so it did a quarter of the search. The review
oracle caught it, because it records the plans that search finds. Fixed, it is **88 ms** on the
desktop (1.9× the TypeScript's 163) and **170 ms** on the iPhone 11 (2.2× its 372).

And the same phone, re-measured with no engine code changed since, ran the sweep in **2.48 s**, not
3.74–3.91 s — one colour in 440 ms, not 660. Nothing in the code explains a third; the phone's state
does (Low Power Mode and heat both throttle), and it cannot be told from here which. The honest
reading is that a sweep costs **2.5–3.9 s** on this phone depending on its state, **1.4–2.2×** faster
than the TypeScript's single 5.45 s measurement — and that a fair ratio needs both apps measured in
one sitting, which has not been done. The phone is 2.7× slower than the desktop for Swift, against 2.4× for
the JavaScript: the gap to the desktop is the hardware, not the language.

**Running it.** `npm run swift-test` runs the whole suite in a release build: 24 tests in about
7 seconds, benchmarks excluded. A plain debug `swift test` takes around 8 minutes, nearly all of it spent in the xcross
and full-plan vector searches, so use the release build as the default. The benchmarks print
timings and assert nothing, so they are left out of it; `npm run swift-bench` runs them.

**On a phone, the benchmark runs from an app, not a test.** Xcode will not run a Swift package's
tests on a physical device — they need a host app, and "tool-hosted testing is unavailable on
device destinations" — which only surfaced when a device run was actually tried. So the workload
is `SweepBenchmark.run()`, public in `CubingCore`, and has two callers that run identical code:

- the `CubingBenchmarks` test target, for the Mac (`npm run swift-bench`), skipped in debug builds;
- `swift/CubingBench`, a one-screen SwiftUI app that runs it on launch, shows the numbers and
  prints them. Open `CubingBench.xcodeproj`, choose the phone, and press Run — its shared scheme
  runs Release, and the screen says so. Relaunch for another cold measurement. Without Xcode:

  ```
  xcodebuild build -project swift/CubingBench/CubingBench.xcodeproj -scheme CubingBench \
    -destination 'id=<device>' -derivedDataPath swift/CubingBench/.build/dd -allowProvisioningUpdates
  xcrun devicectl device install app --device <device> \
    swift/CubingBench/.build/dd/Build/Products/Release-iphoneos/CubingBench.app
  xcrun devicectl device process launch --device <device> --console com.cubingcompanion.bench
  ```

The app is a measuring instrument, not the start of S3's app; it signs with the same personal team
as the Capacitor shell and expires on the same seven-day cycle.

### S3 — The cube link · 2 weekends · needs the cube · **done**

CoreBluetooth replaces the transport seam entirely — no `BleTransport` abstraction, because the
reason it existed was to have two radios behind one interface, and a Swift app has one. Port the
Gen2/3/4 drivers, the move buffer, the timeline fit and the diagnostics recorder.

The committed frame capture is the test: the same 1,213 frames must decode to the same events,
including the 21 recovered-move gaps and the 138 facelet reports.

**Ships:** a Swift app that connects to the cube and mirrors it. The A1 milestone, natively.

**Where it stands.** The protocol, clock fit and tracker are ported as `CubeLink` (a second library
in `swift/CubingCore`) and pass all of a new oracle, `vectors/cubelink.json`. The app is
`swift/CubingApp`: bundle `com.cubingcompanion.native`, shown as *Cubing Native* so it sits beside
the Capacitor app rather than replacing it — which bundle id wins is S4's decision. It builds,
renders, and is installed on the iPhone — and has since been used with the real cube: it connects,
mirrors, and after the recovery fix below keeps up with slice-heavy algorithms.

**The oracle is replays, not pairs.** The drivers are stateful, so each case feeds frames in order
and records what came out after every one — events, the commands the driver chose to send, and
whether it hung up. Six kinds: the real capture decrypted and replayed; every command under both the
GAN and MoYu keys; random messages under every event type for all three generations, with genuine
cube states planted in half the facelet reports (random bytes are almost never a cube, so otherwise
only rejection is exercised, and Gen2's conversion never seen succeeding); MAC recovery; 60 clock
fits; and 40 tracker sessions covering all three desync paths.

**The plan's premise about the capture was wrong.** It contains *no* history responses — 1,063
moves, 138 facelet reports, 11 battery frames and one unknown — because it was recorded on a raw
connection with no driver attached (`captureProtocolFrames`), so nothing ever asked. Its 21 gaps are
real drops that were never recovered; replaying it, the move buffer overflows and the driver hangs up
on 925 frames, because nothing answers. So recovery is tested against a **simulated
cube that answers**: it plays random moves, drops about 8% of frames, and replies to each history
request with a correctly encoded response, sometimes only after the next move arrives. Across six
sessions every played move comes out exactly once, in order, including across the 255→0 wrap. A
first version of the simulation answered at most one request per move and overflowed the buffer in
half its sessions; that measured the simulation, not the driver, and a real cube answers within a
connection interval.

Two things the port found: a history request's count can reach 256, which JavaScript's
`Uint8Array` silently wraps to 0 and Swift's `UInt8(_:)` traps on (the port now wraps, to send the
same byte); and a Gen2 face nibble past `URFDLB` names no face, which `charAt` renders as an empty
string rather than failing. Both are behaviours the vectors pin.

**First field report: slice-heavy algorithms lagged, and the cause was in both implementations.**
Recorded on the phone (the app now records frames and commands in the fixture format, and
`npm run link-replay` decodes one), a session of M-heavy algorithms lost 24% of its moves, against
2% on desktop Chrome: the iPhone link carries about one notification per 45 ms connection event, and
two face turns per slice overrun it. Losing moves was survivable; *holding* them was the bug. The
recovery strategy inherited from `gan-web-bluetooth` held moves for up to 4.5 seconds at the end of a
burst — it asked for nothing more after an answer filled one gap, could not recover a move lost after
one it held, and repeated identical requests whose duplicate answers ate the scarce slots.

The fix is an `eager` recovery mode, in the TypeScript and the Swift alike (see `RecoveryMode` in
`packages/cube-link/src/gan/buffer.ts`); the reference strategy stays the default so the diff
against the library still means something. Its parameters came from a link simulation
(`npm run link-sim`), not from reasoning, and the simulation earned its keep: the first version,
with a 250 ms de-duplication window, was *worse* than the reference under heavy loss, because there
the repeats were doing the job of retries for dropped answers. The shipped version — 100 ms window
plus a 100 ms retry timer — was no worse anywhere tested, and on a saturated link cut the 95th
percentile from 5–10 s to under 0.45 s. Six eager recovery sessions, timer ticks included, are in
`vectors/cubelink.json`, and the port reproduces them.

**Not ported:** the diagnostics recorder. It is the Phase 0 gyro-research tool, and the only Gen4
cube with a gyroscope is the GAN12 ui Maglev — the i Carry 4 has none. Port it if a gyro cube ever
arrives. The drivers still decode gyro frames; nothing records them.

**Running it.** `npm run vectors` needs `--experimental-transform-types` now (in the script): the
drivers use TypeScript parameter properties, which Node's default type stripping rejects and which
vitest had been compiling silently. Open `swift/CubingApp/CubingApp.xcodeproj`, choose the phone,
Run.

### S4 — Recording and history · 2 weekends · **done**

Recorder, session stats, and storage in SwiftData (or SQLite directly — the schema in
`packages/session/src/sqlite.ts` ports as-is). Solve list, per-phase metrics, scoring against the
corpus baselines.

**A migration matters here.** Solves recorded by the Capacitor app live in that app's SQLite
database under a different bundle identifier. Either export/import as JSON through the share sheet,
or keep the bundle id so the container is inherited. Decide before the cutover, not after.

**Ships:** solves recorded, kept and scored, natively.

**Decided:** storage is **SwiftData**, and the Capacitor history is **inherited at the cutover** —
the native app keeps its own bundle id (`com.cubingcompanion.native`) while S4–S5 are built, so both
apps coexist, and takes over `com.cubingcompanion.app` in S6.

**Where it stands.** A third library, `CubingSession`, holds the recorder, session statistics,
per-phase durations, the SwiftData models, the importer and the scramble pool; the app gains a Solve
tab (scramble with progress, live timer, a last-solve card with phase splits and ratings) and a
History tab (per-session best, mean, ao5 and ao12, solve detail with a phase-by-phase
reconstruction, sessions, delete). Built, installed, and used with the real cube: solves are recorded,
kept, timed and scored natively.

- **The oracle** is `vectors/session.json`: 100 scripted sessions at the cube — scrambles turned in
  with slips undone, practice from an arbitrary position, inspection rotations, wasted moves,
  recovered moves with no clock, discards — recording the recorder's state after every step and
  every finished solve's segmentation and phase times; plus 100 statistics cases. The recorder,
  stats and phase durations reproduce all of it.
- **The importer is tested against the real thing.** `vectors/capacitor-solves.sqlite` is written
  by the TypeScript `SqliteSolveStore` through Node's SQLite — the schema and JSON the Capacitor app
  writes — and the drift test checks the file still matches the JSON it was written from. The
  importer reads it with the system SQLite, read-only, and imports into SwiftData idempotently by
  solve id. Checked in the simulator too: with that file placed where the Capacitor app keeps its
  own, the app's first launch brought in all 207 solves and History showed them.
- **One gap the check-the-checks habit caught:** a planted change to the 50-turns-per-second ceiling
  on plausible timing passed, because the corpus had human timing far below it and instant timing
  far above. The generator now turns some solves 15–45 ms apart, straddling the ceiling, and a
  coverage test requires solves at 30–50 TPS.
- **Scrambles** are S1's pool: 10,000 WCA random-state scrambles made by `npm run scrambles` (70 s),
  bundled, and dealt in a seeded shuffle whose position survives relaunches, so none repeats until
  all have been used.

**The cutover, when S6 comes:** set the app target's `PRODUCT_BUNDLE_IDENTIFIER` to
`com.cubingcompanion.app` and build over the Capacitor app. iOS keeps the container, the importer
finds `Documents/cubing-companionSQLite.db` on first launch, and runs once. Solves recorded before
P4 are still in the Capacitor app's WebView IndexedDB, which the importer cannot reach, and the
Capacitor app has no export. If they matter, the Capacitor app needs a one-off IndexedDB-to-SQLite
copy (offered at P4, never done) before the cutover.

### S5 — Planning and review · 2–3 weekends · **built; awaiting use with the cube**

The planner panel, replay with scrubbing, and the A5 decision diff. The largest UI surface and the
most interesting: branch playback with the cube in your hand is better on a phone than it ever was
on a desktop.

**Where it stands.** A solve's detail screen now replays it — scrubbable, with phase bands, from
the grip you most likely held — and lists its decisions: the cross against the optimum and the best
cross with its hold, and each pair choice against the model, with the reasons where they differ and
your execution against the best insertion. Any alternative plays on the replay cube from the moment
it diverges. On the Solve tab, a Plan sheet shows crosses, x-crosses and openings for the colours
chosen, a "which pair" ranking for the cube as it stands, and a practice mode that hides the plan
for the fifteen seconds of inspection. Planning starts the moment a scramble is armed, from the
scramble's own position, so it is usually ready before the scramble is turned in.

- **The review logic moved out of the web worker.** `diffSolve` and the pair ranking lived inside
  `planner.worker.ts`, tangled with its messaging and callable from nowhere else. They are now
  `packages/planner/src/review.ts`; the worker calls them and its tests still pass.
- **The oracle** is `vectors/review.json`: the full decision diff, the inferred grip and the replay's
  move text, and pair rankings at two points, for all twenty real reconstructions, with the shipped
  model weights. Real solves because review is where the frame bookkeeping lives — rotations, wide
  moves, setup rotations — and synthetic solves never reach it.
- **It caught an S2 bug.** `Lookahead.pairs` searched a quarter of the budget the TypeScript does,
  so it found different plans wherever the search runs out of budget. Fixed; the S2 benchmark figure
  it inflated is corrected there.
- **`inferGrip` had `comfortScore`'s tie-breaking bug** — per-turn log sums, so rounding picked
  between grips that saw the same faces. Fixed in both languages the same way.

### S6 — The platform, and the cutover · 1–2 weekends

The things that justified going native in the first place: a Live Activity timing the solve on the
lock screen, a widget for recent times, background BLE if a session should survive a phone call.

Then retire `apps/mobile`. Keep `packages/*` and the vector generators — they are the oracle, and
the differential test does not stop being useful once the port is done.

**Total: 12–16 weekends.** For comparison, P0–P4 were scoped at six and delivered a working iOS
app. This is a larger project than the entire Capacitor migration was.

## What happens to the web app

Frozen, not deleted, and for a concrete reason: the TypeScript packages are the oracle that the
Swift implementation is tested against. Deleting them deletes the reference.

`apps/web` itself can stop being developed the moment S5 reaches parity. It costs nothing to leave
building — it is the thing that proves the packages still run.

## Decision checkpoints

Three points where the honest answer might be "stop":

1. **After S0.** If the planner measures fine on the phone, one of four reasons is gone. The other
   three may still carry it — but the decision should be made knowingly.
2. ~~**After S1.**~~ **Passed.** All three spikes succeeded, and two of the three risks the plan
   identified turned out to be cheaper than assumed rather than harder.
3. ~~**After S2.**~~ **Answered: faster, but not where it was expected to matter.** On the iPhone
   11 the colour-neutral sweep — the number the performance argument was built on — is only 1.4×
   faster (5.45 s → 3.8 s), and P5's preferred-colour default had already brought the everyday case
   to about a second in the Capacitor app. So the performance argument for the rewrite, as
   originally stated, is dead. What survives is narrower and real: cold start, where the cross
   tables drop from 2.2 s to 0.14 s, and the interactive pair lookahead at 4.3×. Neither would
   justify a rewrite alone.

   Restated out loud, as this checkpoint asks: the case for continuing is native feel and platform
   features — CoreBluetooth without a bridge, a Live Activity, widgets, background BLE, SwiftUI —
   with performance as a supporting reason rather than the lead. That was already the stated
   motivation ("a combination of all of these reasons"; "iOS is the real product now"), so it does
   not change the decision; it changes what S3–S6 should be judged on.

## The alternative this rejects, and why

A Swift UI shell running the existing TypeScript core in JavaScriptCore looks like the obvious
middle path and does not work: iOS grants the JIT entitlement only to WKWebView's out-of-process
WebContent process, so in-process JSC runs interpreted. It is the same finding that ruled out React
Native in [MOBILE_PLAN.md](MOBILE_PLAN.md), and it means there is no way to keep the TS core
*running* inside a native app without giving up the performance that motivated going native.

A narrower option remains available if this stalls: keep the Capacitor app and move only the solver
and planner into a native plugin, behind the pure-function boundary they already have. That buys the
compute win for roughly 2,500 lines and none of the UI work — a fallback, not a plan, but a real one.
